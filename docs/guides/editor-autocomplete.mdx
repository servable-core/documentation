# Editor autocomplete & type-checking

Servable apps are plain JavaScript - no TypeScript conversion required to get real editor
autocomplete, inline docs on hover, and a typo flagged before the code ever runs. This is done
entirely through JSDoc and generated `.d.ts` files that every `@servable/*` package now ships,
consumed via a plain `jsconfig.json` with `checkJs` turned on. This guide is the setup, plus what
each generated file actually buys you.

## Wiring `jsconfig.json`

At your app's root (next to `package.json`):

```json title="jsconfig.json"
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "checkJs": true,
    "resolveJsonModule": true,
    "skipLibCheck": true,
    "noEmit": true
  },
  "include": [
    "app/**/*.js",
    "protocols/**/*.js",
    "servable.config.js",
    "node_modules/@servable/server/global.d.ts",
    "node_modules/@servable/parse-server-engine/global.d.ts",
    "servable.schema.types.d.ts",
    "servable.protocols.types.d.ts"
  ]
}
```

:::caution
Do **not** add `"node_modules"` to `exclude` if you also list a `node_modules/...` path in
`include` - TypeScript's explicit `exclude` entries win over explicit `include` entries when they
overlap, so a blanket `node_modules` exclude silently blocks the two `global.d.ts` files above
from ever being read, no error, no warning. If your `include` list is already a precise
allowlist (as above), you don't need a `node_modules` exclude at all.
:::

The two `global.d.ts` files are what make a bare `Servable`/`Servable.App` reference resolve to a
real type without anyone importing anything, split between the two packages: `@servable/server`'s
half (`Services`, `Operations`, `Config`, ...) is engine-agnostic; the engine's half (`Object`,
`Query`, `Cloud`, `User`, ...) is specific to whichever engine your app uses - see the
[engine overview](../reference/engine/overview) for the Parse engine's own surface. Consuming just
`@servable/server` still gives you everything it owns; adding the engine package's `global.d.ts`
sharpens `App` with the real, engine-specific surface.

An editor (VS Code, most others) picks this config up automatically for `.js` files in the same
project - no extension or extra step needed once `jsconfig.json` exists.

## Generating the two `.d.ts` files

Both are generated by `@servable/tools` (installed as a `@servable/cli` dependency already), and
both should be committed alongside `servable.schema.json`, the same way that artifact itself is:

```bash
servable schema types            # -> servable.schema.types.d.ts
servable schema protocol-types   # -> servable.protocols.types.d.ts
```

Committing them matters more than it might look: without `servable.schema.types.d.ts`, generated
class interfaces don't exist to import from, and without `servable.protocols.types.d.ts`,
`Servable.Services.call()` doesn't type-check *at all* (see below for why) - a teammate who
clones the repo and skips running the generator gets real type errors, not just missing
niceties.

See the [`servable schema` command reference](../reference/commands/schema#generate-typescript-types)
for exactly what each reads and when to re-run it.

## What you actually get

### Real fields on `object.get()`/`.set()`

Once `servable.schema.types.d.ts` is generated and included, every class gets a real interface
(field names, real types, `Pointer`/`Relation` fields narrowed to their target class when it's in
the same schema). Nothing wires this to `new Servable.App.Object(...)`'s return type automatically
though - that constructor accepts *any* class name string, by design (see the next section for
why). To get narrowed `.get()`/`.set()`, construct through `Servable.App.Typed` instead:

```js
const reaction = Servable.App.Typed.object('Reaction')
reaction.get('content')               // autocompletes, checked against Reaction's real fields
reaction.get('thisFieldDoesNotExist') // flagged
```

### Why `Servable.App.Object`/`Query` themselves stay untyped for class names

It would be natural to expect `new Servable.App.Object('_Reaction')` (a typo) to be flagged
directly. It isn't, deliberately: a real survey of one app's own code found roughly 235 places
that construct with a *computed* class name - overwhelmingly `new Servable.App.Query(this.className)`,
present in every single subclass's own `class.js`. TypeScript's overload resolution has no way to
validate a literal class name while also accepting an arbitrary computed `string` for those sites
- a fallback loose enough to keep them working is also loose enough to silently accept a bad
literal, which defeats the entire point. `Servable.App.Typed.object(className)`/`.query(className)`
exist as a separate, fully opt-in surface instead - it constructs exactly the same instance the
bare constructor would, just typed. `Object`/`Query` stay the normal, default way to construct;
reach for `Typed` situationally (a one-off script, an unfamiliar class, a migration - somewhere a
wrong class name would be genuinely easy to miss), not as a habit for every construction, which
would just add a second, more verbose way to write the same thing everywhere else. See
[Object reference](../reference/engine/object#typed-validated-construction) for the full detail.

### Real params on `Servable.Services.call()`

Once `servable.protocols.types.d.ts` is generated, `Servable.Services.call({ id, params })`
autocompletes every real service `id` registered across your app's protocols, and narrows `params`
to that service's real `handler` signature (inferred from the handler's own JSDoc, if it has any -
a service with no JSDoc still gets `id` validation):

```js
await Servable.Services.call({
  id: '@my-scope/myprotocol.checkAuth', // autocompletes; a typo here is flagged
  params: { token: 'xyz' },             // checked against that service's real params, if documented
})
```

See [Service reference](../reference/protocol/service#real-autocomplete-on-id-and-params) for the
runtime contract this is typing.

### `defineConfig()` for `servable.config.js`

```js
import { defineConfig } from '@servable/tools'

export default defineConfig({
  id: 'my-app',
  // full autocomplete on every section from here
})
```

A pure identity function at runtime - it exists purely to give the object literal a known type via
JSDoc, so a typo like `evns` for `envs` is flagged at edit time instead of silently producing a
missing config value discovered at boot.

## Linting

`@servable/tools`, `@servable/cli`, `@servable/server`, and `@servable/parse-server-engine` all
ship an ESLint 9 flat config (`eslint-plugin-jsdoc`, `eslint-plugin-n`) rather than the ESLint 6 +
`eslint-config-standard` setup they used previously. If you lint your own app the same way,
`eslint-plugin-n`'s `n/no-missing-import` is worth enabling - it catches a relative import missing
its `.js` extension (or resolving outside the intended package), invisible until Node's ESM loader
throws `ERR_MODULE_NOT_FOUND` at runtime, at lint time instead.
