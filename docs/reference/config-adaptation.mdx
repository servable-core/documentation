# Config Adaptation

This page describes how Servable normalizes and enriches `servableConfig` during startup.

## Adaptation phases

`adaptConfig()` is called twice during `launch()`:

1. Before `launchSystem()` (the docker-compose bring-up).
2. After it, with `live: true`, once `launchSystem()`'s own dynamically-detected connection
   details (database URIs, ports reassigned by `getPortNear` when a declared port wasn't free)
   have already been merged into `servableConfig.envs`.

Both calls run the exact same `basic()` defaulting pass and the same
`engine.setConfigurations({ servableConfig, live, engine })` hook, but `basic()` guards itself
with `servableConfig.adaptedBasic`: the very first line returns immediately if that flag is
already set, so its defaulting logic only actually executes once per process, on the first call.
The second call exists so `engine.setConfigurations()` (which is *not* guarded the same way, since
some engine hooks legitimately need to see the post-`launchSystem()` state) gets a chance to react
to the live payload.

## What gets normalized

The basic adaptation layer (first call only) sets defaults for:

- `dryRun` behavior and matcher function.
- `system.docker`, per-key, not "is the whole object missing": setting only
  `system.docker.namespace` (see [protocol system](./protocol/system)) must not silently drop the
  `enabled`/`environments` defaults just because the caller already provided *a* `system.docker`
  object.
- `protocols.local` resolution paths.
- `rootProtocolPayload` defaults.
- runtime `envs` values (server host/port/url, keys, verbosity, cache URIs), each via `envOr(process.env.X, default)`,
  so an explicitly-set env var always wins over the hardcoded default.

Note what's *not* here any more: there is no `distribution` or `utilsDatabaseURI` handling in
this layer (removed with the separate utils database — see
[Schema Migrations](../guides/schema-migrations) and [Seed](./protocol/seed)). The engine resolves
its own database URI directly (preferring `servableConfig.envs.databaseURI`, the same
preserve-if-set pattern this layer still uses for its other `envs` values, over the raw env var)
when it builds its state store — there's no separate URI for this file to default.

`basic()` marks `servableConfig.adaptedBasic = true` on completion, which is what makes the second
call's invocation a no-op.

## Engine hook

After basic normalization, engine-specific configuration is applied through:

- `engine.setConfigurations({ servableConfig, live, engine })`

This allows engine adapters to inject framework-runtime specifics without changing app declarations.

## Practical implications

1. Missing optional config fields can still produce runnable defaults.
2. Environment values can override many runtime settings.
3. Startup behavior can differ between initial and live adaptation phases.
4. Debugging config issues should include both adaptation points in lifecycle.
