# Model Lifecycle

This page describes the runtime lifecycle around model classes in Servable.

## Class registration flow

During launch, model classes are registered before schema wiring is completed.

High-level flow:

1. Protocol graph is computed in schema build.
2. Class registration runs for protocol-managed classes.
3. Trigger hooks are attached to class lifecycle events.
4. Routes, functions, jobs, services, and live behavior are wired.

## Trigger lifecycle for models

Per class, current wired trigger operations are:

- `beforeSave`
- `afterSave`
- `beforeDelete`
- `afterDelete`

`beforeFind` and `afterFind` are present in code (commented out) but not active in default wiring.
`_Session` is explicitly skipped entirely - no triggers are ever wired for it.

Class-level trigger methods are looked up under both casings (`beforeSave` and `beforesave`,
`afterDelete` and `afterdelete`, etc.) - either naming convention works.

## Trigger execution order

For each lifecycle event: the protocol-level trigger handler runs first, then the class-level
trigger handler, when present.

For `beforeSave`, `beforeDelete`, and `afterDelete`, both calls are properly `await`ed inside a
`try`/`catch` that logs `[Class <name>] ⚠️ <event>` on failure - an error there is caught and
visible.

**`afterSave` is different, and it matters**: both the protocol-level and class-level `afterSave`
calls are made *without* `await`, still inside the same `try`/`catch` wrapper. Because the calls
aren't awaited, a promise rejection from either one happens after that `try`/`catch` has already
exited - it is never caught by it. Concretely: **an error thrown inside an `afterSave` trigger
(protocol- or class-level) does not get logged by the `[Class <name>] ⚠️ afterSave` handler at
all**; it becomes a silent unhandled promise rejection instead. This is the exact same class of gap
documented in [Route and job contracts](../route-job-contracts) for `Route.define()` - an
async function called without `await` inside a try/catch that therefore cannot catch what it
throws. If an `afterSave` side effect needs to be reliable and observable on failure, don't assume
this wiring's own `catch` will tell you when it breaks.

The whole registration function itself is wrapped in one more try/catch that swallows
`ERR_MODULE_NOT_FOUND` silently (no trigger module for this class is a normal, expected case) but
logs any *other* error and continues - meaning a class whose trigger module fails to import for a
different reason ends up with no triggers wired at all, with only a console error to notice it by.

## Practical guidance

1. Put reusable data invariants in protocol triggers.
2. Keep class triggers focused on model-specific behavior.
3. Avoid expensive operations inside `beforeSave`.
4. Use jobs for heavy asynchronous side effects.
