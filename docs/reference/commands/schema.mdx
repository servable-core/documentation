# $ servable schema

Manages `servable.schema.json`, the app's committed schema artifact — a git-tracked snapshot of
every protocol's schema, built and diffed entirely offline (no database involved). The running
server reads this same file at boot to validate that what's deployed matches what was committed,
and to enforce that a schema never regresses what an older, still-running pod may depend on
during a rolling deploy.

Every command in this group operates only on local files. Applying a schema to a live database,
and refusing to boot when a build is incompatible, both happen in the server at launch — not here.

## Build the artifact

Compiles every protocol's `schema.json` into `servable.schema.json`, carrying forward whatever
`compatibilityFloor` and `breakingChanges` were already committed.

```bash
servable schema build
```

Run this after adding or changing any protocol's `schema.json`, then commit the result.

## Diff against what's committed

Compares the committed artifact against what `schema build` would produce right now, and
classifies every difference as one of:

- **SAFE** — additive (new class, new field, widened permissions, a field newly marked
  `deprecated`). Applies automatically; no gate needed.
- **BREAKING, pre-deprecated** — a field or class being removed that was already marked
  `deprecated: true` in a prior commit. Eligible for `schema contract`.
- **BREAKING, not deprecated** — a type change, a newly-required field, an index change, or a
  removal that was never deprecated first. Never applied automatically.

```bash
servable schema plan
```

### Options

```bash
  --ci   Exit non-zero on any breaking change (for use in a build/CI step)   [boolean]
```

### Example

```bash
servable schema plan --ci
```

Since this never touches a database, it's meant to run as a pre-push hook or a CI step — a
breaking schema change gets caught in the PR itself, before it reaches a running server.

## Apply safe changes

Rebuilds the schema and rewrites `servable.schema.json` — but only if every change since the last
commit is additive. Refuses outright if anything breaking is present.

```bash
servable schema apply
```

If this refuses, run `schema plan` to see what's breaking. A removal only becomes applyable once
it's been marked `deprecated: true` in an earlier release — see `schema contract` below.

## Remove a deprecated field or class

The only command in this group allowed to remove anything, and the only one that advances
`compatibilityFloor`. Requires the field/class being removed to have already been marked
`deprecated: true` in a *previously committed* artifact — not the one you're building right now.

```bash
servable schema contract --reason="superseded by nature, deprecated since 2026-08"
```

### Options

```bash
  --reason   Why this removal is safe now (recorded in the artifact for CI/review)   [string] [required]
      --force    Allow removing a field/class that was never marked deprecated       [boolean]
```

`--force` bypasses the deprecation check for something known to be safe regardless (e.g. added and
removed within the same release, never actually deployed). `--reason` is required either way —
every contraction is recorded, never silent.

Running this bumps `compatibilityFloor` by one. Any pod built against an older schema will refuse
to boot rather than run against a database it doesn't know is missing fields it expects — see
[Schema Migrations](../../guides/schema-migrations) for how that check works at launch.

## Typical workflow

1. Change a protocol's `schema.json` (add a field, or mark one `deprecated: true`).
2. `servable schema plan` to see what changed and whether it's safe.
3. `servable schema apply` (additive changes) or `servable schema contract --reason=...` (a
   deprecated removal), then commit `servable.schema.json`.
4. Deploy. The server refuses to boot if the artifact is missing, out of date, or has a lower
   `compatibilityFloor` than what's already recorded for the database it's connecting to.
