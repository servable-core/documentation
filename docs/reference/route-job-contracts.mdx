# Route and Job Contracts

This page summarizes the effective runtime contracts for protocol routes and jobs.

## Route contract matrix

| Field | Required | Meaning | Notes |
|:--|:--|:--|:--|
| `method` | Yes | HTTP method (`get`, `post`, `put`, `patch`, `delete`, `head`, `options`, `trace`, `function`) | Lowercased at registration |
| `path` or `paths` or `url` | Yes | Route path(s) | Paths are sanitized and lowercased |
| `handler` | Yes | Async handler | Executed through HTTP processing wrapper |
| `prefix` | No | Route namespace | Prepended before path |
| `schema` | No | Request/response contract | Used by route validation flow |
| `cache` | No | Route-level caching | Applied to read-oriented methods |
| `rateLimiting` | No | Request throttling | Supported across methods |
| `request.type` | No | Body parser content type | Defaults to `application/json` |
| `servableArguments` | No | Extra runtime args | Added by server wiring in common route flow |

### Route behavior notes

1. Route paths are sanitized with path normalization and forced to lowercase.
2. `function` method is mapped to `/function/{path}` style endpoints.
3. Body parser raw mode is used for mutating verbs by default.
4. **`Route.define()` is async and must be awaited by its caller.** It's an async function, so any
   exception thrown inside it (building the cache middleware, the rate-limiter, anything before
   the route is actually registered) becomes a rejected Promise, not a synchronous throw. If the
   caller doesn't `await` the call, that rejection is never caught: the route silently never
   registers, with no error logged anywhere, and requests to it 404 as if the path was never
   declared. This is easy to miss because everything else about the boot can look completely
   successful. Always `await Servable.App.Route.define(...)`.

## Job contract matrix

Backed by [Agenda](https://github.com/agenda/agenda) (`@hokify/agenda`), MongoDB-persisted.

| Field | Required | Meaning | Notes |
|:--|:--|:--|:--|
| `id` | Yes | Job identifier | Used as the scheduler job name |
| `handler` | Yes | Async job handler | Executed by the scheduler worker |
| `cron` | Yes (current adapter behavior) | Schedule expression | Passed straight through to Agenda |
| `priority` | No | Job priority | Defaults to `high` |
| `concurrency` | No | Concurrent executions | Defaults to `10` |
| `defaultConcurrency` / `maxConcurrency` | No | Agenda-level concurrency tuning | Forwarded to Agenda unchanged |
| `defaultLockLimit` / `lockLimit` / `defaultLockLifetime` | No | Agenda locking behavior | Forwarded to Agenda unchanged |
| `processEvery` | No | Polling interval | Forwarded to Agenda unchanged |
| `ensureIndex` / `sort` | No | Agenda job-collection tuning | Forwarded to Agenda unchanged |
| `timeZone` | No | Cron timezone | Forwarded to Agenda unchanged |
| `attributes` | No | Additional payload | Passed on scheduled invocation |
| `onComplete` | No | Completion callback | Forwarded to Agenda unchanged |
| `runOnInit` | No | Run immediately on registration | Defaults to `false` |

### Job behavior notes

1. Jobs are registered through the engine job adapter.
2. Scheduler storage depends on the Parse database URI configuration.
3. Jobs are started and scheduled during startup wiring.

:::caution
Each `Servable.App.Jobs.define()` call currently creates its **own** `Agenda` instance - its own
MongoDB connection and its own polling loop - rather than sharing one per app. An app with several
protocol jobs ends up with that many independent connections/polling loops doing overlapping work.
Confirmed in `register/jobs/index.js`; tracked as a known issue, not yet fixed.
:::
